# M8: Hermes builds skills, you approve them

## Goal
Hermes Agent (in WSL2) can write, test and submit skills through an MCP server. Only you can
switch one on, from the dashboard (or `flins skills enable`), after FLINS re-checks it on
Windows.

Acceptance (SPEC §14): Hermes builds a sample skill end to end. It can't write outside
`_incoming`, and it can't enable anything.

## Isolation (why it's built this way)
The dashboard's page token stops other *websites*, not local programs. If Hermes could reach
Windows' `127.0.0.1`, it could read a page, take the token and approve things. Same for
running `flins.exe` through WSL interop, or reading `.env` / `data/` through `/mnt/c`. So:

| Wall | Setting (docs/HERMES.md) |
|---|---|
| No Windows files | `/etc/wsl.conf`: `[automount] enabled = false`; only `skills/_incoming` is mounted (fstab) |
| No Windows programs | `[interop] enabled = false` |
| No dashboard | WSL networking stays **NAT** (not mirrored): WSL can't reach Windows' 127.0.0.1. `flins doctor` warns if `.wslconfig` says mirrored |
| No messaging | Hermes' gateways (WhatsApp, Telegram, …) off |

So the MCP server runs **inside WSL** (a copy of this repo, `flins skilldev`, stdio). It sees
only the shared `_incoming` folder, the starter skills as examples, and the **example**
policy for the safety eval. It never opens `data/`, `.env` or your config.

## Pieces
| Piece | Files | Notes |
|---|---|---|
| Workspace | `skilldev/workspace.py` | All tool logic. Path confinement: skill names `[a-z][a-z0-9_]`, relative paths of plain parts, allowed file types, size limits, no symlinks, resolved path must stay in `_incoming/<name>`. |
| Shared checks | `skills/checks.py` | validate → fixtures in the sandbox → 162-case eval with the skill on. Used by `flins skills test`, the MCP server and the dashboard. |
| MCP server | `skilldev/server.py`, `flins skilldev` | Official `mcp` SDK (2.x `MCPServer`), stdio. Tools from SPEC §10 plus `delete_skill_file`, `list_requests`, `read_request`. No enable/approve/policy/data tool exists. |
| Submissions | `_incoming/_submissions/<name>.json` | Hermes' claim (summary, hash, its test report). Untrusted: the dashboard shows it labelled as such and re-runs everything. |
| Review | `skilldev/review.py`, `web/templates/skills*.html` | `/skills`: installed, waiting for review, requests. `/skills/review/<name>`: what it may do, what's new vs the approved version, diff, fixture results, Hermes' summary. **Approve** (token + the hash you looked at) re-runs validate + fixtures + eval, copies it into `skills/<name>`, pins it in `skills.lock`, audits. **Reject** with a note Hermes can read. |
| Requests | `core/commands.py` | "make a skill that …" (voice / self-chat) → `_incoming/_requests/<id>.md` for Hermes. No confirmation needed: it sends nothing. |

## Tests
Path confinement (`..`, absolute, drive letters, backslashes, dot files, wrong types, symlinks,
size); the tool list has no enable/approve/policy/data tool; an in-process MCP client playing
Hermes scaffolds, writes, tests and submits a skill; it can't enable it; approval refuses a
changed hash, a failing skill or a bad token; approve installs + pins + audits; reject keeps it
off and leaves a note; requests are written and listed.

## Demo
`uv run flins skilldev` under an MCP client (or the test that plays Hermes), then the
dashboard's Skills page → review → approve.
